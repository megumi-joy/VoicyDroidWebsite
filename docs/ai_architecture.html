Voicy Ecosystem Architecture

A unified manifesto and technical guideline for AI Agents working within the VoicyDroid infrastructure.

CRITICAL RULE FOR AI AGENTS: DO NOT MANUALLY REBUILD, RE-DOWNLOAD, OR STORE DOCKER CONTAINERS OR ENGINE BINARIES (LIKE GODOT) ON GITHUB OR LOCAL HOST FILESYSTEMS. USE THE ESTABLISHED VOICY CLOUD ARCHITECTURE AND PRE-BUILT CONTAINERS.

1. The Container Philosophy

The VoicyDroid ecosystem is designed around API-driven builder containers. When the user requests a modification to a game (e.g., the Train Visual Novel, the Crypto Sandbox) or a heavy data generation task, the AI should NOT download Godot locally or write new Dockerfiles from scratch.

Instead, the AI must use the existing containers stored in the Cloud Registry. These containers are already configured by previous agents (like ABAF) with all dependencies pre-installed.

2. Existing Cloud Registry Images

The following images are continuously maintained in the Google Artifact Registry and are available on the host machine:

Blender 3D Agent:
ai-blender-agent:latest

3. Agent Workflow Instructions

When tasked with modifying, building, or deploying a game inside the Voicy ecosystem, follow this exact flow:

  1. Analyze the Source Code: Use standard file viewing tools to read the game's source (e.g., games/train/godot_vn).
  2. Edit Code: Modify the scripts, assets, or scenes as requested.
  3. Trigger the Container via API/CLI: Do not run the Godot binary locally. Instead, invoke a Docker command or Voicy API call that mounts the project directory into the godot-agent:latest container, and let the container export the WebAssembly build.
  4. Commit the Results: Commit the source code changes and the output WebAssembly to the frontend repository (VoicyDroidWebsite).
Note to Agents: Always check docker images on the host system to see the exact tag names available before attempting to build anything new.
